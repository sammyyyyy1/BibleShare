# Social Core — Plan 3: Friends — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship symmetric friendship end-to-end — request a friend by exact `@username` (with reciprocal auto-accept and a structural dedupe guarantee), accept/decline incoming requests, see friends and pending requests in a Friends sheet, and see friends' `shared_to_timeline` encouragements on Home — while closing the world-readable `profiles` enumeration hole.

**Architecture:** Four SQL migrations (embed FKs → unordered-pair unique index → friend RPCs → `profiles` lockdown + discovery RPC), applied via the Supabase MCP to project `jstdoizgosatitptyrdy`. `friendships` keeps **no** INSERT/UPDATE/DELETE policy, so `SECURITY DEFINER` RPCs are the only write path (defense-in-depth is asserted, not assumed). On the client, a protocol-seamed `FriendService` + `FriendsViewModel` + `FriendsView` sheet hang off HomeView's existing `person` tab; `FeedService.fetchTimeline` drops its client-side `author_id` filter so `posts_select_visible` RLS alone gates the Home feed. The tag picker's `resolveExact` keeps its signature but is re-routed through the new `find_profile_by_username` RPC so it survives the `profiles` lockdown.

**Spec (source of truth):** `docs/superpowers/specs/2026-07-17-friends-design.md` (approved). This plan implements that spec task-by-task; where prose here disagrees with the spec, the spec wins.

**Tech Stack:** Supabase (Postgres 17), Supabase MCP tools (`apply_migration`, `execute_sql`, `get_advisors`), Swift 6 / SwiftUI, iOS 17 target, `supabase-swift` (SPM, `from: 2.0.0`), Swift Testing (`import Testing`), XcodeGen.

## Task 2: Unordered-pair dedupe index

The directional PK `(requester_id, addressee_id)` does not prevent `A→B` and `B→A` as two rows. This unique index on the *unordered* pair is the structural guarantee the spec (§4.2) demands; the RPC's `unique_violation` retry (Task 3) leans on it. The directional PK stays — it carries who-requested-whom.

**Files:**
- Create: `supabase/migrations/20260717010100_friendships_dedupe.sql`

- [ ] **Step 1: Write the migration file**

```sql
-- friendships is empty in prod, so this builds without violations.

  (least(requester_id, addressee_id), greatest(requester_id, addressee_id));
```

## Task 3: `send_friend_request` + `respond_to_friend_request` RPCs

The entire friend write surface. `friendships` keeps no write policies, so these `SECURITY DEFINER` RPCs are the only way in. `send_friend_request` resolves the username internally (works after Task 4's lockdown), auto-accepts a reciprocal pending request, is idempotent on duplicate sends, and falls back through `unique_violation` for the insert race.

**Files:**
- Create: `supabase/migrations/20260717010200_friend_rpcs.sql`

- [ ] **Step 1: Write the migration file**

`supabase/migrations/20260717010200_friend_rpcs.sql`:

```sql
-- Friend write path. friendships has NO insert/update/delete RLS policies, so
-- these RPCs are the only write boundary; SECURITY DEFINER is safe because the
-- caller's identity comes from auth.uid(), never from a parameter.

create or replace function public.send_friend_request(p_addressee_username text)
returns public.friendships
language plpgsql
security definer
set search_path = public
as $$
declare
  v_uid  uuid := auth.uid();
  v_them uuid;
  v_row  public.friendships;
begin
  if v_uid is null then
    raise exception 'authentication required' using errcode = '28000';
  end if;

  -- Resolve the username here (bypasses the profiles lockdown; exact match only).
  select id into v_them
  from public.profiles
  where lower(username) = lower(btrim(coalesce(p_addressee_username, '')))
  limit 1;

  if v_them is null then
    raise exception 'username not found' using errcode = '22023';
  end if;

  if v_them = v_uid then
    raise exception 'cannot send a friend request to yourself' using errcode = '22023';
  end if;

  -- Already friends (either direction)?
  if exists (
    select 1 from public.friendships
    where status = 'accepted'
      and ((requester_id = v_uid  and addressee_id = v_them)
        or (requester_id = v_them and addressee_id = v_uid))
  ) then
    raise exception 'already friends' using errcode = '22023';
  end if;

  -- Reciprocal pending (them -> me): auto-accept theirs, never a second row.
  select * into v_row
  from public.friendships
  where requester_id = v_them and addressee_id = v_uid and status = 'pending';

  if found then
    update public.friendships
       set status = 'accepted', responded_at = now()
     where requester_id = v_them and addressee_id = v_uid
    returning * into v_row;
    return v_row;
  end if;

  -- My own pending request (me -> them): idempotent.
  select * into v_row
  from public.friendships
  where requester_id = v_uid and addressee_id = v_them and status = 'pending';

  if found then
    return v_row;
  end if;

  begin
    insert into public.friendships (requester_id, addressee_id)
    values (v_uid, v_them)
    returning * into v_row;
    return v_row;
  exception when unique_violation then
    -- A reciprocal them->me pending row raced in between the checks above and
    -- this insert (trips friendships_unordered_uniq): accept it instead.
    update public.friendships
       set status = 'accepted', responded_at = now()
     where requester_id = v_them and addressee_id = v_uid and status = 'pending'
    returning * into v_row;
    if found then
      return v_row;
    end if;
    -- Otherwise the pair row exists in some other shape (our own duplicate
    -- raced, or the reciprocal was accepted concurrently): return it as-is.
    -- friendships_unordered_uniq guarantees at most one row for the pair.
    select * into v_row
    from public.friendships
    where (requester_id = v_uid  and addressee_id = v_them)
       or (requester_id = v_them and addressee_id = v_uid);
    return v_row;
  end;
end;
$$;

create or replace function public.respond_to_friend_request(p_requester_id uuid, p_accept boolean)
returns void
language plpgsql
security definer
set search_path = public
as $$
declare
  v_uid uuid := auth.uid();
begin
  if v_uid is null then
    raise exception 'authentication required' using errcode = '28000';
  end if;

  if coalesce(p_accept, false) then
    update public.friendships
       set status = 'accepted', responded_at = now()
     where requester_id = p_requester_id
       and addressee_id = v_uid
       and status = 'pending';
    if not found then
      raise exception 'no pending friend request from that user' using errcode = '22023';
    end if;
  else
    -- Decline deletes the row; idempotent (already-gone is a no-op).
    delete from public.friendships
     where requester_id = p_requester_id
       and addressee_id = v_uid
       and status = 'pending';
  end if;
end;
$$;

revoke execute on function public.send_friend_request(text) from public, anon;
grant  execute on function public.send_friend_request(text) to authenticated;
revoke execute on function public.respond_to_friend_request(uuid, boolean) from public, anon;
grant  execute on function public.respond_to_friend_request(uuid, boolean) to authenticated;
```

- [ ] **Step 4: Fresh request → one pending row; duplicate send is idempotent**

Assert inside a `do` block: any mismatch raises an ERROR (which `execute_sql` surfaces); success returns no rows. This is the reliable idiom here — `execute_sql` only returns the *last* statement's result, so multi-`select` steps can't be observed column-by-column. `mcp__supabase__execute_sql`:

```sql
begin;
  set local role authenticated;
  do $$
  declare r public.friendships;
  begin
    perform set_config('request.jwt.claims',
      '{"sub":"aaaaaaaa-0000-0000-0000-000000000001","role":"authenticated"}', true);
    r := public.send_friend_request('bob');
    if r.status <> 'pending' then raise exception 'FAIL: fresh send status=%', r.status; end if;
    -- Duplicate (case-insensitive) send returns the same pending row — no new row.
    r := public.send_friend_request('BOB');
    if r.status <> 'pending' then raise exception 'FAIL: dup send status=%', r.status; end if;
    if (select count(*) from public.friendships) <> 1 then
      raise exception 'FAIL: expected exactly 1 friendship row, got %',
        (select count(*) from public.friendships);
    end if;
  end $$;
rollback;
```

Expected: no error (empty result). Any `FAIL:` means the RPC's fresh/idempotent path is wrong. (The count runs as `authenticated` alice; `fr_select_parties` shows only her own edge.)

- [ ] **Step 5: Reciprocal request auto-accepts into a single row**

The two sends **must** share one transaction — alice's pending row has to persist for carol's reciprocal call to see and auto-accept it (a `rollback` between them would discard it and the auto-accept would never fire). `auth.uid()` follows the `request.jwt.claims` GUC, so switching that GUC mid-transaction re-impersonates without committing. `mcp__supabase__execute_sql`:

```sql
begin;
  set local role authenticated;
  do $$
  declare r public.friendships;
  begin
    perform set_config('request.jwt.claims',
      '{"sub":"aaaaaaaa-0000-0000-0000-000000000001","role":"authenticated"}', true);
    r := public.send_friend_request('carol');            -- alice -> carol
    if r.status <> 'pending' then raise exception 'FAIL: alice send=%', r.status; end if;

    perform set_config('request.jwt.claims',
      '{"sub":"cccccccc-0000-0000-0000-000000000003","role":"authenticated"}', true);
    r := public.send_friend_request('alice');            -- carol -> alice: auto-accept
    if r.status <> 'accepted' then raise exception 'FAIL: reciprocal=%', r.status; end if;
    if r.responded_at is null then raise exception 'FAIL: responded_at is null'; end if;

    if (select count(*) from public.friendships
        where least(requester_id, addressee_id)
              = least('aaaaaaaa-0000-0000-0000-000000000001'::uuid,'cccccccc-0000-0000-0000-000000000003'::uuid)
          and greatest(requester_id, addressee_id)
              = greatest('aaaaaaaa-0000-0000-0000-000000000001'::uuid,'cccccccc-0000-0000-0000-000000000003'::uuid)
       ) <> 1 then
      raise exception 'FAIL: expected exactly one row for the pair (dedupe broke)';
    end if;
  end $$;
rollback;
```

Expected: no error. A `FAIL:` on `reciprocal` means the auto-accept branch didn't fire; a `FAIL:` on the pair count means a second row was created (the dedupe guarantee broke). The count runs as carol, who sees the accepted row as its addressee.

- [ ] **Step 7: respond — addressee-only accept; decline deletes; decline idempotent**

Two self-contained transactions; each seeds its pending row directly (service role) so nothing depends on writes from a rolled-back step, then drives the RPC under impersonation inside a `do` block (top-level `PERFORM` is PL/pgSQL-only). `mcp__supabase__execute_sql`:

```sql
-- (a) A non-addressee cannot accept; the addressee can.
begin;
  insert into public.friendships (requester_id, addressee_id, status)
    values ('dddddddd-0000-0000-0000-000000000004','bbbbbbbb-0000-0000-0000-000000000002','pending');
  set local role authenticated;
  do $$
  declare r public.friendships;
  begin
    -- alice is NOT the addressee of dave->bob: must be rejected.
    perform set_config('request.jwt.claims',
      '{"sub":"aaaaaaaa-0000-0000-0000-000000000001","role":"authenticated"}', true);
    begin
      perform public.respond_to_friend_request('dddddddd-0000-0000-0000-000000000004', true);
      raise exception 'NON-ADDRESSEE DID NOT FIRE';
    exception when sqlstate '22023' then null; end;

    -- bob IS the addressee: accept sets status + responded_at.
    perform set_config('request.jwt.claims',
      '{"sub":"bbbbbbbb-0000-0000-0000-000000000002","role":"authenticated"}', true);
    perform public.respond_to_friend_request('dddddddd-0000-0000-0000-000000000004', true);
    select * into r from public.friendships
      where requester_id = 'dddddddd-0000-0000-0000-000000000004'
        and addressee_id = 'bbbbbbbb-0000-0000-0000-000000000002';
    if r.status <> 'accepted' or r.responded_at is null then
      raise exception 'FAIL: accept did not set accepted/responded_at (status=%)', r.status;
    end if;
  end $$;
rollback;
```

```swift
import Foundation

@MainActor
@Observable
final class FriendsViewModel {
    private(set) var edges: [FriendEdge] = []
    private(set) var isLoading = false
    private(set) var isAdding = false
    /// Sheet-level failures (load/respond).
    var errorMessage: String?
    /// Success note under the add-friend field ("Request sent." / "You're now friends.").
    var addStatus: String?
    /// Failure note under the add-friend field.
    var addError: String?
    /// Client-side filter text for the friends list (no server call).
    var searchText = ""

    let myID: UUID
    private let service: FriendServicing

    init(myID: UUID, service: FriendServicing = FriendService.shared) {
        self.myID = myID
        self.service = service
    }

    /// Pending requests others sent me.
    var incoming: [FriendEdge] { edges.filter { $0.status == .pending && $0.addresseeID == myID } }
    /// Pending requests I sent.
    var outgoing: [FriendEdge] { edges.filter { $0.status == .pending && $0.requesterID == myID } }
    /// Accepted friendships (either direction).
    var accepted: [FriendEdge] { edges.filter { $0.status == .accepted } }

    /// Case-insensitive substring match across username and display name,
    /// like mainstream social apps — but strictly over the already-accepted
    /// friends list (adding stays exact-username-only).
    var filteredFriends: [FriendEdge] {
        let query = searchText.trimmingCharacters(in: .whitespacesAndNewlines).lowercased()
        guard !query.isEmpty else { return accepted }
        return accepted.filter { edge in
            guard let person = edge.otherParty(myID: myID) else { return false }
            return person.username.lowercased().contains(query)
                || (person.displayName?.lowercased().contains(query) ?? false)
        }
    }

    func load() async {
        guard !isLoading else { return }
        isLoading = true
        errorMessage = nil
        defer { isLoading = false }
        do {
            edges = try await service.fetchEdges(userID: myID)
        } catch {
            errorMessage = PostError.message(for: error)
        }
    }

    func addFriend(username: String) async {
        let cleaned = username
            .trimmingCharacters(in: .whitespacesAndNewlines)
            .trimmingCharacters(in: CharacterSet(charactersIn: "@"))
        guard !cleaned.isEmpty, !isAdding else { return }
        isAdding = true
        addStatus = nil
        addError = nil
        defer { isAdding = false }
        do {
            let friendship = try await service.sendRequest(username: cleaned)
            addStatus = friendship.status == .accepted ? "You're now friends." : "Request sent."
            await load()
        } catch {
            addError = PostError.message(for: error)
        }
    }

    func respond(requesterID: UUID, accept: Bool) async {
        do {
            try await service.respond(requesterID: requesterID, accept: accept)
            await load()
        } catch {
            errorMessage = PostError.message(for: error)
        }
    }
}
```
